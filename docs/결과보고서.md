## 1. 과제 목적 및 필요성

국내 주요정보통신기반시설(이하 주통기) 점검은 한국인터넷진흥원(KISA)의 「주요정보통신기반시설 기술적 취약점 분석·평가 방법 상세가이드」를 사실상 단일 표준으로 삼는다. 그러나 연간 기술 점검 항목이 478개를 넘고, 2026년 개정으로 신규 운영체제와 가상화 환경을 포함한 12개 분야로 점검 범위가 확대되었다. 한편 2024년 국내 사이버 침해사고는 1,887건으로 전년 대비 48% 증가해 위협 환경이 빠르게 악화되고 있다. 보안 가이드는 고도화되었으나 점검 방식은 여전히 사람이 항목을 하나씩 직접 진단하는 수동 방식에 머물러 점검 인력에 과부하가 발생한다.

기존 자동화 방식도 한계가 뚜렷하다. 단순 셸 스크립트에 기반한 규칙 단독 방식은 "불필요한 서비스 제거"처럼 정책 판단이 필요한 항목을 처리하지 못한다. 반대로 거대언어모델(LLM) 단독 방식은 토큰 비용이 크고 판정 일관성이 떨어진다. 두 방식 모두 단독으로는 정확성과 비용을 동시에 만족시키지 못한다.

본 과제의 목적은 규칙과 LLM을 결합해 정확성, 비용, 일관성을 동시에 확보하는 주통기 자동 진단 시스템을 개발하는 데 있다. 임계값과 문자열 비교만으로 판정 가능한 항목은 규칙이 직접 처리하고, 정책 판단이 필요한 항목만 LLM에 위임하며, 여기에 취약 항목의 조치 자동화와 가이드라인 개정에 따른 자가 갱신까지 포함한다. 국가기반시설 보안의 중요성이 커지는 가운데 보안 인력 부족과 점검 품질 편차 문제를 해소하고 점검을 표준화한다는 점에서 본 과제의 필요성이 있다.

## 2. 작품 제작 과정

제작은 요구 분석에서 시작하였다. KISA 「주요정보통신기반시설 기술적 취약점 분석·평가 방법 상세가이드」를 분석해 운영체제별 점검 항목과 판정 기준을 정리하고, 시스템이 갖추어야 할 기능을 도출하였다. 이 과정에서 각 항목을 임계값·문자열 비교만으로 판정할 수 있는 규칙 가능 항목과 사람의 정책 판단이 필요한 항목으로 구분하고, 규칙으로 판정할 수 없는 항목만 LLM에 위임하는 양호·취약·미판정 3-class 판정 정책을 설계하였다. 대상 점검 항목은 Windows Server, Windows PC, 그리고 Linux를 포함한 Unix 계열에 걸쳐 정의하였다.

이어 가이드라인 데이터를 시스템에 적재하는 단계를 진행하였다. 가이드라인 PDF를 pdfplumber와 PyMuPDF로 파싱해 항목코드, 점검 기준, 조치 방법 등을 구조화하고, 이를 PostgreSQL 데이터베이스에 저장하였다. 항목코드를 키로 삼아 점검 결과와 가이드라인 본문을 곧바로 연결할 수 있도록 설계함으로써, 이후 판정 단계에서 별도의 검색 과정 없이 가이드라인 원문을 판정 근거로 활용할 수 있게 하였다.

다음으로 점검과 판정의 핵심 로직을 구현하였다. 먼저 임계값이나 문자열 비교만으로 양호·취약을 결정할 수 있는 항목에 대해 규칙 기반 점검 스크립트를 작성하였다. 정책 판단이 필요한 항목은 LLM에 위임하도록, 규칙이 1차로 판정한 뒤 정책 판단 항목만 LLM이 2차로 재판정하는 판정 엔진을 구현하였다. AI 엔진으로는 별도의 API 키 없이 호출할 수 있는 Gemini CLI를 사용하였으며, 데이터베이스의 가이드라인 본문을 프롬프트에 직접 주입해 검색·임베딩 단계 없이 맥락 기반 판정이 이루어지도록 하였다. LLM은 위임받은 항목을 항상 양호와 취약 중 하나로 결정하고, 정보가 부족할 때는 보수적으로 취약으로 판정하도록 하여 판정 누락을 방지하였다.

취약으로 판정된 항목에 대해서는 자동 패치 모듈을 개발하였다. LLM이 조치 스크립트를 자동 생성하고, 실행이 실패하면 오류 메시지를 입력으로 받아 스크립트를 다시 작성하는 과정을 최대 세 번까지 반복하는 재작성 루프를 구성하였다. 생성된 스크립트는 MCP의 파일 기록 기능으로 저장한 뒤 컴파일과 실행의 2단계로 검증하였고, 패치 전후의 점검값을 다시 수집해 조치가 실제로 반영되었는지 확인하도록 하였다. 시스템 손상을 일으킬 수 있는 위험 명령은 사전 차단 규칙으로 막아 안전성을 확보하였다.

또한 가이드라인 개정에 자동으로 대응하기 위한 자가 갱신 기능을 구현하였다. 새 가이드라인 PDF가 업로드되면 이전 버전과 diff로 비교해 추가·수정·삭제 항목을 감지하고, 신규·수정 항목에 대해서는 Gemini가 점검 스크립트를 자동 생성하며, 삭제 항목은 자동으로 반영하도록 하였다. 사용자 접점에서는 FastAPI와 Jinja2 기반의 웹 대시보드를 구현해 점검 시작과 진행률 확인, 판정 결과 조회, 이전 진단과의 비교를 한 화면에서 수행할 수 있게 하였다. 점검 스크립트는 실행 시점에 운영체제를 감지해 Linux·Solaris·AIX·HP-UX 네 가지 Unix 계열 각각에 맞는 설정 파일과 명령을 자동 선택하도록 통합하였다.

개발 전 과정에서는 생산성을 높이기 위해 AI 코딩 어시스턴트인 Claude Max를 유료 구독해 활용하였다. 점검 스크립트 작성, 디버깅, 리팩터링, 문서 정리와 같이 반복적이고 작업량이 많은 부분을 AI의 보조를 받아 수행함으로써, 제한된 학기 일정 안에서 170여 개에 이르는 점검 항목과 여러 모듈을 구현하고 통합할 수 있었다. 다만 AI가 생성한 코드와 산출물은 그대로 사용하지 않고 팀원이 직접 검토·수정하고 실제 환경에서 동작을 검증한 뒤 시스템에 반영하였다.

각 모듈은 팀원이 분담해 개발한 뒤 통합 어댑터를 거쳐 하나의 플랫폼으로 결합하였다. 마지막으로 LLM 단독, 규칙 단독, 제안 시스템 세 가지 판정 방식을 동일한 데이터셋에 적용한 통합 테스트와 성능 평가를 수행하였다. 비결정성을 고려해 각 방식을 여러 차례 반복 측정하고 일치율, 평균 토큰, 항목당 시간, 일관성의 네 지표로 비교함으로써 제안 시스템의 정확성과 효율성을 정량적으로 검증하였다.

## 3. 작품개념, 구성 및 상세내용

본 작품은 규칙 기반 점검과 LLM 판정을 결합한 주통기 취약점 자동 진단·패치 플랫폼이다. 임계값이나 문자열 비교만으로 판정할 수 있는 항목은 점검 스크립트가 직접 양호·취약을 결정하고, 사람의 정책 판단이 필요해 규칙으로 판정할 수 없는 항목만 LLM에 위임한다. 이로써 단순 셸 스크립트가 처리하지 못하는 정책 판단 항목까지 자동화 범위에 포함하면서, LLM 단독 방식이 가진 토큰 비용과 판정 일관성 문제를 함께 줄인다.

시스템은 관리자 흐름과 사용자 흐름을 가이드라인 데이터베이스 하나로 연결한다. 관리자 흐름에서는 새 가이드라인 PDF를 업로드하면 이를 파싱하고 이전 버전과 diff(추가·수정·삭제)를 비교한 뒤, 신규·수정 항목의 점검 스크립트를 자동 생성한다. 사용자 흐름에서는 점검을 시작하면 운영체제를 감지(Check OS)한 다음 점검 스크립트를 실행해 결과를 JSON으로 수집하고, 규칙 또는 LLM으로 판정한다. 판정 결과는 Result DB에 저장되어 이전 이력(Past Result DB)과 비교되며 웹 대시보드에 표시된다. 취약 항목에는 LLM이 패치 스크립트를 생성해 실행한다.

3대 핵심 기능은 다음과 같다.

- 맥락 이해 판정: 규칙으로 1차 판정한 뒤 LLM이 2차 재판정하는 구조이다. 가이드라인 본문을 데이터베이스에서 조회해 별도 검색·임베딩 단계 없이 프롬프트에 직접 주입함으로써 오탐과 환각을 동시에 억제한다.
- 조치 자동화: 취약 항목의 조치 스크립트를 LLM이 자동 생성하고, 실행이 실패하면 오류 메시지를 받아 스크립트를 다시 작성하는 과정을 최대 3회 반복한다. 패치 전후 재수집으로 결과를 검증하며, 시스템 손상을 유발할 수 있는 위험 명령은 사전 차단 규칙으로 방어한다.
- 가이드라인 자가 갱신: 신규 가이드라인 PDF를 자동 파싱하고 이전 버전과 diff를 비교한 뒤, 신규·수정 항목의 점검 스크립트를 자동 생성하고 변경·삭제 항목을 자동 반영한다.

판정 정책은 양호·취약·미판정의 3-class를 따르되, LLM은 위임받은 항목을 항상 양호와 취약 중 하나로 결정하며 정보가 충분치 않으면 보수적으로 취약으로 판정한다. 또한 점검 스크립트는 실행 시점에 운영체제를 감지해 KISA가 함께 다루는 Linux·Solaris·AIX·HP-UX 각각에 맞는 설정 파일과 명령을 자동 선택함으로써 4개 Unix 계열을 단일 스크립트로 통합 대응한다.

기술 스택은 AI 엔진으로 Gemini CLI(gemini-2.5-flash)와 MCP 서버를, 웹·백엔드로 FastAPI·Jinja2·WeasyPrint/ReportLab·matplotlib를 사용한다. 데이터는 PostgreSQL에 저장하며 PDF 파싱에는 pdfplumber/PyMuPDF를 활용한다.

성능 평가는 Windows 79개 항목을 대상으로 세 가지 판정 방식을 10회 반복 측정해 일치율, 평균 토큰/항목, 항목당 시간, 일관성의 네 지표로 비교하였다.

| 방식 | 일치율(%) | 평균 토큰/항목 | 항목당 시간(s) | 일관성(%) |
|---|---:|---:|---:|---:|
| LLM 단독 | 96.84 | 232.4 | 28.07 | 88.61 |
| 규칙 단독 | 86.08 | 0.0 | 0.00 | 100.00 |
| 제안 시스템 | 97.34 | 38.9 | 6.12 | 98.73 |

규칙 단독은 정책 판단 항목을 미판정으로 처리해 일치율이 86.08%에 그쳤고, LLM 단독은 항목당 평균 28.07초·232.4 토큰을 소모하면서 일관성도 88.61%에 머물렀다. 반면 제안 시스템은 정책 판단 항목에만 LLM을 호출해 LLM 단독 대비 토큰 약 83%·시간 약 78%를 절감하면서 일치율 97.34%와 일관성 98.73%를 동시에 달성하여, 정확성·효율성·안정성의 균형이 가장 우수하였다.

## 4. 기대효과 및 활용방안

본 시스템의 기대효과는 다음 네 가지 축으로 정리된다.

- 점검 비용·시간 절감: 119개 항목 기준으로 수작업 시 수 시간이 걸리던 점검을 병렬 처리로 약 1분까지 단축한다. 외부 보안 컨설팅 의존도가 낮아져 연간 점검 비용이 줄고, 보안 인력은 단순 점검에서 벗어나 취약점 조치·분석 등 고부가가치 업무에 집중할 수 있다.
- 점검 품질의 표준화: 규칙과 LLM의 자동 판정으로 점검자 역량에 따라 달라지던 결과 편차를 제거해 일관된 보안 수준을 확보한다. 이전 진단 결과와 비교하는 기능으로 보안 상태의 변화를 추적할 수 있다.
- 보안 접근성 확대: 보안 전문 인력이 부족한 중소기업·공공기관·교육기관도 웹 대시보드 기반 UI로 손쉽게 자가 점검을 수행할 수 있어 진단 진입장벽이 낮아진다. 이는 국가 차원의 주통기 보안 수준 상향에 기여한다.
- 확장 가능성: 점검 대상을 네트워크 장비, 컨테이너·쿠버네티스, 클라우드(AWS·Azure)로 넓히고, ISMS-P·CIS Benchmark 등 타 보안 가이드라인으로 룰셋을 확장할 수 있다.

활용방안 측면에서 본 시스템은 보안 인력이 부족한 중소기업·공공기관·교육기관의 자가 점검 도구로 우선 활용된다. 나아가 ISMS-P·CIS Benchmark 등 타 보안 가이드라인으로 룰셋을 확장하고 SIEM/SOAR 등 기존 보안 솔루션과 연동함으로써, 단일 진단 도구를 넘어 통합 보안 운영 체계로 발전할 수 있다.

## 6. 지도교수(담당교수) 종합평가

> 아래는 지도교수 작성란에 참고할 수 있는 초안입니다. 양환석 교수님께서 검토·수정하여 사용하시면 됩니다.

본 과제는 주요정보통신기반시설 취약점 점검이 가진 수동 진단의 비효율과 인력 과부하라는 현실 문제를 명확히 포착하고, 규칙 기반 점검과 거대언어모델(LLM) 판정을 결합한 하이브리드 접근으로 이를 해결하였다는 점에서 문제 정의와 해결 방향이 타당하다. 단순 규칙으로 처리 가능한 항목은 스크립트가 직접 판정하고 정책 판단이 필요한 항목만 LLM에 위임하는 구조는, 규칙 단독과 LLM 단독 방식이 각각 가진 한계를 균형 있게 보완한 설계로 평가된다.

기술적으로도 점검 자동화에 그치지 않고 조치 스크립트 자동 생성과 재작성 루프, 가이드라인 개정에 대응하는 자가 갱신, 4개 Unix 계열에 대한 단일 스크립트 대응까지 구현해 시스템의 완성도가 높다. 특히 세 가지 판정 방식을 동일 데이터셋에 적용해 일치율, 토큰 비용, 처리 시간, 일관성을 정량적으로 비교한 성능 평가는 제안 방식의 우수성을 객관적으로 뒷받침하며, 학부 캡스톤 과제로서 충실한 검증 과정을 보여 주었다.

팀원들은 가이드라인 파싱, 데이터베이스, 판정 엔진, 자동 패치, 웹 대시보드 등 모듈을 분담해 개발하고 이를 하나의 플랫폼으로 통합하는 협업 역량을 발휘하였다. 다만 정답 라벨의 절대 정확도 검증과 Linux 계열에 대한 정량 평가, 외부 LLM 호출에 대한 의존도 완화는 향후 보완이 필요한 부분이다. 이러한 과제가 보완된다면 실제 현장에 적용 가능한 수준의 보안 자동 진단 도구로 발전할 수 있을 것으로 기대된다. 전반적으로 문제 인식, 설계, 구현, 검증의 전 과정을 충실히 수행한 우수한 과제로 평가한다.
