## 1. 서론 (15줄 이내, 짧게)

### 들어갈 내용

1. **배경** (3~4줄)
   - KISA 주요정보통신기반시설 가이드라인은 Linux/Windows/Unix 등 다양한 환경의 보안 점검 항목을 정의 (총 200+ 항목)
   - 현재 대부분 수작업 또는 단순 스크립트 — 점검자 1인이 수십~수백 항목 수동 검사

2. **문제** (5~6줄)
   - 단순 스크립트의 한계: "불필요한 서비스 제거" 같은 **정책 판단 항목**은 자동화 불가 → 항상 수동 결정
   - LLM 단독 사용의 한계: ① 토큰 비용 (모든 항목 LLM 호출), ② 일관성 부족 (같은 입력에 다른 출력), ③ 단순 양호 항목까지 LLM 호출하는 비효율
   - 기존 자동 패치 도구는 Windows 의 UAC 권한 승격을 처리하지 못하거나, Linux 의 4개 Unix 계열(linux/solaris/aix/hpux)을 통합 지원하지 않음

3. **본 연구 기여** (3~4줄)
   - **규칙 + LLM 하이브리드 판정** — 단순 임계값/문자열 매칭으로 가능한 양호/취약 판정은 코드 안에서 즉시 처리, 정책 판단 항목만 LLM에 위임 ("규칙불가" 클래스)
   - **UAC 자동 승격 + Gemini 재작성 루프** — 패치 실행 실패 시 LLM이 stderr를 보고 재작성 (최대 3회)
   - **4-OS 통합 단일 스크립트** — `platform.system()` 으로 자동 감지, OS별 config 파일·명령어 매핑

## 2. 본론 (전체의 70% 이상)

### 2.1 시스템 아키텍처 (그림 1)

**그림 1 — 데이터 흐름 다이어그램**:
```
PDF 가이드라인
   ↓ (PyPlumber 파서, integration/euni_adapter.py)
forensic_db.vulnerabilities
   ↓ (한 방향 sync, transform + dedupe)
vs_guideline_items (PostgreSQL)
   ↓ (LLM 프롬프트에 직접 주입, RAG 미사용)
점검 스크립트 실행 (Windows / Linux 4-OS / PC)
   ↓ vs_scan_results
규칙 기반 1차 판정 (양호 / 취약 / 규칙불가)
   ↓ 규칙불가만 LLM 호출 (Gemini CLI)
vs_judgments (양호 / 취약, reason, patch_script)
   ↓ 사용자가 "패치" 클릭
UAC 승격 + Gemini 재작성 루프 → vs_patch_executions
```

설명 (4~5줄):
- 가이드라인 데이터는 단일 진실 원천(SoT) `vs_guideline_items` 에 저장.
- 항목코드(item_code) 1:1 조회로 LLM 프롬프트에 직접 주입 → 벡터 검색·임베딩 불필요 → 토큰 효율↑, 정확성↑
- 4가지 모듈(가이드라인/Windows+백엔드/Linux 엔진/웹 UI)이 `integration/` 어댑터 4개를 통해 결합

### 2.2 판정 파이프라인 (3-class 정책)

핵심 원칙:
- 점검 스크립트는 가능한 부분은 직접 양호/취약 판정 (`result` 키)
- 정책 판단 필요 항목 → `result: "규칙불가"` → LLM 후처리에 위임
- LLM 은 항상 양호/취약 둘 중 하나로 결정 (불확실 시 보수적으로 취약)

규칙불가 분류 기준:
1. 본질적 정책 판단 (예: "불필요한 서비스 제거" 의 "불필요한" 정의)
2. 서비스/계정/파일 목록처럼 사람이 보고 결정해야 하는 항목
3. 가이드라인 텍스트가 모호해 자동 판정 불가능

가이드라인은 LLM 프롬프트에 직접 주입 (RAG 미사용 정당화 1줄):
> 항목코드 1:1 조회가 가능하므로 벡터 유사도 검색이 불필요하며, 가이드라인 전체를 프롬프트에 그대로 포함시켜 컨텍스트 손실 없이 정확한 판정 유도.

- Hybrid 는 두 장점을 결합 — 토큰 절감 + 정책 판단 처리

### 2.4 자동 패치 + 4-OS 분기 (특이점)

- **UAC 자동 승격**: Windows 패치는 `Start-Process -Verb RunAs` 로 권한 상승 후 실행
- **Gemini 재작성 루프**: 실행 실패 시 LLM 이 stderr 를 보고 패치 스크립트를 재작성 (최대 3회 재시도)
- **안전장치**: 위험 패턴 (`Remove-Item -Recurse`, `Format-Volume`, BitLocker 키 변경 등) 차단
- **4-OS 단일 스크립트**: `platform.system()` 으로 linux/solaris/aix/hpux 감지, OS별 config 파일·명령 매핑 (예: 패스워드 정책은 Linux days, Solaris/AIX weeks)

## 통계 수집 방법 (TBD 채우는 작업 — 별도)

논문 수치 확보를 위해 다음을 측정:

1. **데이터셋**: 동일한 79개 Windows 항목 (또는 72개 Linux 항목) 의 점검 결과 100건 샘플
2. **방식별 호출**:
   - LLM only: 모든 항목을 `result="규칙불가"` 로 강제 → 전부 LLM 호출
   - Rule only: 점검 스크립트 결과만 사용, "규칙불가" 는 그대로 두고 정확도 측정 (규칙불가는 오답 처리)
   - Hybrid: 현재 시스템 그대로
3. **측정 지표**:
   - 정확도 = 사람이 라벨링한 정답 vs 시스템 판정 일치율
   - 토큰: Gemini API 응답의 input/output 토큰 합산
   - 시간: 항목당 평균 ms (네트워크 시간 제외)
   - 일관성: 같은 항목 3회 호출했을 때 동일 결과 비율

자동화 스크립트 위치 (작성 예정):
- `vulnerability-scanner/eval/compare_methods.py` (신규) — 3가지 방식을 같은 데이터로 호출하고 표 1 출력
